# 页面 → 模块映射表

> **这是什么**：把「用户看到的原型页面」和「后台能力模块」对齐——原型按任务组织，开发按模块组织，本表是中间层。  
> **依据/关联**：[PRD.md](./PRD.md) · [功能结构与业务流程.md](./功能结构与业务流程.md) · [角色与功能清单.md](./角色与功能清单.md) · [业务文档写作规范.md](./业务文档写作规范.md)  
> **用法**：新增/改页面时先补一行；评审时业务看「用户任务」，开发看「主责/协作模块」。

## 业务设定

### 一句话

**页面 ≠ 模块。** 一个页面可能是多个模块的「操作入口」；一个模块也可能服务多个角色、多个页面。

### 怎么读本表

1. **原型页面**：按侧栏菜单路径写，与 `prototype/index.html` 一致。  
2. **用户任务**：用户来这页要完成什么（评审用，不写接口名）。  
3. **主责模块**：这页的核心业务能力归谁；改动应优先落在这个模块。  
4. **协作模块**：这页会调用但不由本页拥有的能力。  
5. **数据归属**：这条数据的「唯一真源」在哪个模块；页面只读展示或发起动作，不另存一份。

### 能力模块清单（技术向 · 稳定命名）

> 模块名用**业务能力**，不用页面名。新增页面时从下面选，不随意造新模块。

| 模块 ID | 模块名 | 职责（一句话） | 数据真源 |
|---------|--------|----------------|----------|
| M01 | 身份与权限 | 登录、角色、员工菜单裁剪、数据范围 | 账号、权限配置 |
| M02 | 用户与归属 | 骑手档案、服务运营商、渠道归属 | 用户主档、归属关系 |
| M03 | 订单 | 套餐单、换电单、渠道商订单、状态机 | 订单表 |
| M04 | 支付与退款 | 收单、原路退、退款审批 | 支付流水、退款单 |
| M05 | 清分与分账 | 支付成功后实时清分、1% 计提 | 清分记录 |
| M06 | 额度池 / 人天 | 批发、分配、消耗扣天 | 额度池、人天账本 |
| M07 | 设备与物联网 | 电柜/电池只读、三元组上报 | 设备快照（IoT 写入） |

### 映射原则（PM 自检）

| 原则 | 说明 |
|------|------|
| 先任务后模块 | 先写清用户任务，再填模块；禁止「有个页面就先建个模块」 |
| 主责唯一 | 每页只有一个主责模块；协作模块可多个 |
| 写操作走主责 | 列表页的「同意/驳回/编辑」由主责模块提供能力，页面只做编排 |
| 三台账不混 | 资金实收、清分、摊销/提现分模块展示，不在一屏混算 |
| 平台能力复用 | 同一模块服务多角色时，差异放在权限与数据范围，不复制逻辑 |

## 新增页面 · 填空模板

> 复制下面一行到对应角色表格，或新建小节。

```markdown
| {菜单路径} | {用户来完成什么} | M{xx} {模块名} | M{xx}, M{xx} | {哪张表/哪个域是真源} | {创建/变更的关键事件} | {一期/二期} |
```

### 填写检查清单

- [ ] 用户任务是否可独立朗读（不含字段名、接口名）  
- [ ] 主责模块是否唯一  
- [ ] 协作模块是否都已存在于「能力模块清单」  
- [ ] 是否与现有页面重复造轮子（应复用模块而非复制页面逻辑）  
- [ ] 一期/二期是否与 [角色与功能清单.md](./角色与功能清单.md) 一致  
- [ ] 原型 `index.html` 侧栏路径是否与本表一致  
- [ ] 若涉及钱：是否标明清分/退款/提现由哪个模块负责

## 实现附录（开发用）

### A. 页面 → 模块 → 服务（示意）

> 服务名仅为示例，以实际代码仓库为准。本表帮助后端划边界，不替代 API 文档。

| 模块 ID | 建议服务域 | 典型 API 职责 |
|---------|------------|---------------|
| M03 订单 | order-service | 套餐/换电单 CRUD、状态机 |
| M04 支付与退款 | payment-service | 预下单、回调、退款 |
| M05 清分 | settlement-service | 实时清分、1% 计提、冲正 |
| M06 额度池 | quota-service | 采购、分配、消耗 |

| M09 保证金 | deposit-service | 账户、扣款顺序 |
