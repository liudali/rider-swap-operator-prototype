# 业务文档写作规范（可读优先）

> **这是什么**：规定产品文档如何写成「人能读懂的业务设定 + 开发附录」。  
> **示范**：[骑手电池押金.md](./骑手电池押金.md) · [天数池.md](./天数池.md) · [换电范围策略.md](./换电范围策略.md)

## 业务设定

### 一句话
业务读者只读「业务设定」；字段名、伪代码、决策索引放进「实现附录」。

### 必须与禁止
见下文专节。面板「本页关键设定」优先抽业务设定层。

## 实现附录（规范全文）


> 适用：`docs/` 下产品规则、PRD 业务章节、面板「本页关键设定」所抽真源。  
> 示范：[骑手电池押金.md](./骑手电池押金.md) · [天数池.md](./天数池.md) · [换电范围策略.md](./换电范围策略.md)  
> 决策：decision-088

## 读者优先

| 读者 | 读哪一层 |
|------|----------|
| 评审 / 运营 / 新人 | **业务设定**（必须能独立读懂） |
| 开发 / 测试 | **实现附录**（字段、枚举、公式、决策链接） |

一篇文档默认结构：

1. 文首「依据」区（决策链接、范围一句）  
2. **业务设定**（场景、规则、落位、例外）  
3. **实现附录**（可折叠阅读习惯上放文末）

## 必须

- 用「谁、在什么时候、做什么、结果怎样」写规则。
- 后台落位写清菜单路径，如：订单与服务 → 用户押金。
- 例外单独成条，不塞进主句括号里堆决策号。
- 表格用于**对照理解**（类型说明、角色差异），不是数据字典堆砌。

## 禁止（业务层正文）

- 把英文字段名当主语：如 ``depositRefundMode=auto``、``userOwner``、``valid_from``。
- 大段伪代码 / 赋值公式代码块（可放附录）。
- 句中夹 `decision-0xx`（决策集中写在文首「依据」或附录「决策索引」）。
- 用页面代号代替路径：如只写 `P04` 不写「购套餐页」。

## 推荐改写对照

| 差（像伪代码） | 好（可朗读） |
|----------------|--------------|
| ``depositRefundMode=auto`` → 原路退 | 运营商若选「自动退款」，确认后系统按原支付路径退回 |
| ``type=押金退还`` | 退款管理中类型为「押金退还」的申请 |
| `valid_to = valid_from + D - 1` | 从支付当天起算，含首尾共 D 个自然日，末日 23:59 结束 |

## 与文档面板

- 「本页关键设定」优先抽取 **业务设定** 下的条目。
- 附录默认不当作摘要主来源。

## 改写节奏

先改摘要卡高频真源（押金、退款、渠道结算、天数池），再铺开；新文档直接按本规范写。
