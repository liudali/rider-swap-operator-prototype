## 1. 结论

平台后台已形成「协议 / 用户 / 订单 / 设备 / 流水 / 运营商 / 保证金 / 统价」主干，**多数列表可查、关键写操作表单可开**；资金与 IoT 相关能力仍明显分期。整体完成度约 **列表层 70%+，履约细节与资金闭环 40%～50%**。

最大产品口径差：线上提现仍是「人工线下打款 + 登记流水」，与产品原型近期口径（工单审核后向支付渠道发转账指令、工单带转入卡号）不一致。

## 3. 分模块验证结果

### 3.1 认证与主体

| 项 | 结果 |
|----|------|
| 手机号+密码登录 | 通过 |
| 多组织选择（平台 / 运营商） | 通过 |
| 切换账号 | 入口可见 |

字段：登录仅手机号、密码，合理。主体卡展示组织名+角色，清晰。

### 3.2 协议管理（亮点）

**协议配置**

- 表头：协议编码 / 管理名称 / 发布状态 / 草稿状态 / 启停 / 更新时间 / 操作
- 操作：历史记录、编辑草稿、发布、停用/启用
- 规则文案清楚：发布不可改；场景只能引用已启用已发布协议
- 新建协议字段：协议编码、管理名称、标题、正文（HTML 白名单）→ **合理**

**同意记录**

- 表头：留痕编号、业务动作编号、用户、场景、已同意协议、同意时间、客户端版本
- 筛选项：用户编号/手机/姓名/客户端/场景/协议/同意时间
- 提示：只追加；正文以版本 ID + SHA-256 固定 → **合规向设计到位**

### 3.3 用户管理

**骑手信息表头（偏全）**  
骑手、实名认证、骑手状态、服务运营商、用户类型、电池押金、押金状态、套餐/权益、服务状态、生效周期、渠道商、持有电池、操作

| 问题 | 严重度 | 说明 |
|------|--------|------|
| 持有电池「功能暂未接入」 | 中 | 列已占位但无数据，易误导客服 |
| 认证申请 Tab 与骑手信息列几乎同构 | 中 | 待审队列应收敛为审核专用列（材料、驳回原因、操作=通过） |
| 实名弹窗身份证照片「加载失败」 | 中 | 演示/权限/存储需排查 |
| 「部分字段暂未接入」总提示 | 低 | 诚实，建议逐列灰态或隐藏未接列 |

查看实名信息字段：认证状态、姓名、身份证号（脱敏）、性别、民族、出生日期、住址、签发机关、证件有效期、照片 → **要素齐全**。出现「已终止」状态，需与「未通过/已注销」枚举对齐文档。

### 3.4 订单管理

**套餐购买订单**

- 表头合理：订单号、用户、售卖运营商、站点、套餐、服务状态、生效周期、总额、订单状态
- 筛：服务状态筛选标「未接入」→ 应隐藏或禁用
- 详情大量「未接入」：关联柜机、已换电次数、免押、冻结、退款公式 → 详情页信息架构超前于实现

**换电订单（完成度最高之一）**

- U/C/B 三元组 + 跨网服务费列已落地
- 详情含站点柜机、还入/取出电池、进度时间线、权益来源跳转套餐单
- SOC/健康度仍为 —（IoT 未接）

**渠道商订单**

- 人天池批发单：人天、单价、金额、银行流水号、状态、申请/到账/关闭时间
- 平台只读、运营商确认到账 → 权责文案正确
- 未见链接类购卡订单分 Tab（若本期只做了人天池，侧栏名「渠道商订单」略宽）

### 3.5 设备管理

| 页 | 通过点 | 问题 |
|----|--------|------|
| 电柜 | 批量导入、编辑、二维码绑定；有台账计数 | 在线状态未接 IoT；站点/城市多为 — |
| 电池 | 批量导入；型号 ID 列 | SOC/SOH/位置未接；型号常为 — |
| 电池型号 | 编码/名称/电压/容量/启停；停用不删历史 | 新增默认电压 48、容量 20，容量默认值是否业务确认 |

### 3.6 流水 / 平台账户

| 页 | 结果 |
|----|------|
| 用户支付记录 | 套餐支付/退款有数据；额度充值、待审核未接；部分行「历史快照缺失」 |
| 运营商之间 | 日清账单、应付/应收/净额、保证金扣款来源 → 概念正确 |
| 平台提成(待开发) | 有 C 端分账行，但示例费率出现 **50% / ¥0.01**，需核对是否测试费率或展示错误 |
| 平台账户(待开发) | Mock：余额带「月末·可提现」副文案；商户号脱敏展示 |

### 3.7 运营商管理

**新增/编辑运营商字段**

- 基本：Logo、名称、账号手机、城市、状态、联系人、电话、**邮箱**、办公地址、备注
- 收款：开户银行（锁定招商银行）、开户名称、商户号、**门店号**、银行账号、开户支行、联行号（选填）
- 文案：银行可后补；一旦填写则除联行号外必填 → 合理
- 初始密码提示 `Swap@2026` → 演示可接受，正式环境应随机+强制改密

| 字段问题 | 建议 |
|----------|------|
| 邮箱 | 产品原型曾去掉邮箱；现网仍有，确认是否要保留 |
| 开户银行只读招商 | 若全网统一通道可接受；否则应可选银行 |
| 门店号 | 需在 PRD 明确与商户号关系 |
| 列表保证金/信用展示夹杂「单位：分」 | **展示 bug**，应对用户显示元 |

**渠道商管理**：结算模式（链接类/人天池）、登录账号、签约运营商 → 监管向只读合理；经营摘要多为 —

**提现审核（重要口径）**

- 表头：申请单号、运营商、金额、到账账户、申请时间、审核状态、打款状态、银行流水号、平台确认时间
- 流程：人工线下打款 →「登记打款」填流水号+凭证+备注
- 筛选项占位「请输入审核状态/打款状态」→ 应为枚举下拉，文案像文本框
- **缺失相对新产品口径**：转出账户、转账银行卡号、审核通过后向支付渠道发指令；现网是线下登记模型

**平台服务费**：C/B 比例、生效日期、状态 → 合理；列表大量 0.00%+停用，需确认默认策略

### 3.8 保证金

- 充值确认：待确认/已处理；金额、转账日、流水号、付款户 → 合理；当前待确认空
- 账户总览：清分收款专户信息 + 运营商保证金/信用/档位封顶/占用/跨网；支持补录到账、调信用
- 变动明细：充值等流水可查

### 3.9 平台统价

- 跨网服务费 / 人天标准日值：全网默认 + 城市覆盖 + 待生效版本 → 与产品「不追溯、城市覆盖优先」一致
- 预警短信：人天余额不足规则；默认阈值 10 人天、间隔 1440 分、最多 3 次 → 需与「可用 < 在职×10」口径核对是否同一规则

## 4. 字段合理性总评

**做得好**

- 多数页有「说明」与未接入诚实标注
- 协议版本不可变 + 同意留痕摘要，适合合规审计
- 换电三元组与跨网费在列表/详情贯通
- 运营商收款账户「可后配 / 开填则必填」边界清楚
- 统价「当前生效 / 待生效」分离清楚

**建议优先修**

1. 提现：明确一期是否坚持线下打款；若对齐新产品，补转入卡号与转账指令态  
2. 运营商列表金额单位（分/元）展示错误  
3. 提现筛选项改为枚举下拉，修正 placeholder  
4. 用户/订单详情隐藏或折叠「未接入」字段，避免客服误用  
5. 平台提成示例 50% 费率核查  
6. 平台账户去掉或改掉「月末·可提现」Mock 文案  
7. 邮箱、门店号写入正式字段清单或下线  
8. 认证申请 Tab 独立列与操作，勿复用全量用户表头

## 5. 与产品原型的主要差距（平台视角）

| 原型能力 | 测试环境 |
|----------|----------|
| 提现工单 → 通道转账指令 + 转入卡号 | 线下打款登记 |
| 设备改归属纠错 | 未见入口 |
| 用户待审认证独立队列体验 | 有认证申请 Tab，列未收敛 |
| 总览 / 营销 / 租赁公司等 | 未见或未在平台侧栏 |
| 平台账户真实营收 | 标待开发 + Mock |
